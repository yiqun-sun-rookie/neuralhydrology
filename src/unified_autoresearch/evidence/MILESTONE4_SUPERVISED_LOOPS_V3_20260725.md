# 里程碑四：监督下的两次完整循环与停机策略标定（2026-07-25）

## 结论

在真实开发数据上，开着独立监督**连跑两次完整纵向循环**（各 4 类候选 × 2 协议 × {训练,预测} = 16 个已登记运行），
两次都通过五项门槛、四个安全灯全灭、每次运行全程受监督、无受控停止，且两次的科学产物逐字节一致。
过程中暴露并修复了一个真实的停机策略缺陷：旧的绝对 4 吉字节系统内存下限落在本机正常内存波动带内，
会因外部压力误停仅占 26 兆字节的候选。新增 `resource_safety_v3` 改为**按任务相对判断**，
在真实内存下探到 2.87 吉字节（低于旧下限）的条件下不再误停。本文件不宣称任何候选超过任何基线。
复核后（见 §六）又按测试先行修掉三处严谨性弱点，强化后的运行门槛改为依赖**从原始访问日志独立复算的禁止访问数**，在真实数据上仍为 `true`。

## 一、v2 首次真实受控停止 = 标定信号

首轮监督下的连跑中，第一次运行（`supervised_development_loop_real_v1`，旧策略）完整跑通，
第二次（`supervised_development_loop_real_v2`，旧策略）在 `fusion/forward/train` 被监督**真实触发受控停止**：

- STOP_REQUEST 原因：系统内存连续多次低于停机下限。采样序列 4.02 → 3.953 → 3.727 吉字节，连续两次跌破旧的 4 吉字节绝对下限。
- 候选自身峰值内存仅 **0.026 吉字节**；压力来自外部程序，不是候选造成的，候选也无法通过停止自己来缓解。
- 退出码 75、状态 `checkpointed`：候选存好检查点后优雅退出，符合冻结的受控退出契约。

这是监督进程**第一次在真实运行中实际停下真实候选**（此前只有测试证据），既证明刹车可用，
也暴露刹车线标错了位置。两份旧策略产物按“污染/异常快照不清理、不覆盖”留存，作为标定证据。

## 二、根因与 `resource_safety_v3`

**根因**：旧 `resource_safety_v1` 用绝对系统内存下限（4 吉字节）判停，与候选自身占用无关。
本机 31.7 吉字节内存、空闲约 7 吉字节、负载下探约 3.7 吉字节，这条 4 吉字节的线正好压在正常波动带里，
任何后台程序一动就被踩到，专停这种几十兆字节的小候选。

**改法**（新增文件 `protocols/resource_safety_v3.json`，不修改冻结的 v1）：内存判停改为按任务相对，只在下列之一连续两次成立时停：

1. **候选可自救的危险**：候选自身占用超过它声明的包络（`estimated_peak_memory_gb + memory_safety_reserve_gb`）的 1.5 倍。
2. **系统真正近乎耗尽**：可用内存低于 1.5 吉字节的近-耗尽下限（设在正常波动带以下），或低于总量的 4%。

磁盘判停不变（低于 10 吉字节立即停）。启动前判断沿用“任务声明 + 当前容量”。运行器由 v1 改指向 v3；
监督发布的归属身份新增候选的声明内存预算，供按任务相对判断使用。

## 三、测试先行的改动

- 新增回归测试 `test_external_system_pressure_does_not_stop_a_small_candidate`：把 v2 的真实误停钉成回归——
  系统可用内存 3.7 吉字节、候选 0.026 吉字节时不停。
- 新增 `test_candidate_that_exceeds_its_declared_envelope_is_stopped`：候选超己声明包络时按“候选”原因停。
- 改写 `test_monitor_requires_consecutive_near_out_of_memory_samples_before_stopping`：近-耗尽下限连续两次才停。
- 更新受监督发布身份测试：MONITOR_TARGET 现含 `declared_memory_budget_gb`，并断言其等于声明峰值加余量。
- `run_full_development_loop` 早前已加可选监督参数（测试先行，见提交前工作树）。

## 四、v3 下两次完整循环与校验

产物：`supervised_development_loop_v3_r1`、`supervised_development_loop_v3_r2`；
校验器 `scripts/verify_supervised_real_loops.py` 输出落于 r1 的 `VERIFICATION.json`。

| 项 | v3_r1 | v3_r2 |
|---|---|---|
| 五项门槛（退出码/产物16·8·32/有限指标/禁止读取0/登记校验） | 全过 | 全过 |
| 独立复算的禁止访问数（从每个运行原始访问日志重算，非读循环自报） | 0 | 0 |
| 循环自报的四个安全标记（自声明，仅存档，**不计入通过门槛**） | 全灭 | 全灭 |
| 全程受监督的运行数 | 16 / 16 | 16 / 16 |
| 受控停止 | 0 | 0 |
| 采样期最低系统可用内存（吉字节） | 3.80 | **2.87** |
| 实测进程峰值内存（吉字节） | 0.1376 | 0.1367 |

- **两次科学子集（8 份评分 + 4 份汇总 = 12 个文件）逐字节一致**；监督日志为活测量，天然各自不同，不在一致性判据内。
- 关键实证：v3_r2 系统可用内存最低探到 **2.87 吉字节，低于旧的 4.0 吉字节下限**——旧策略下会像 v2 一样被停，
  v3 下（下限 1.5）安然跑完。v3 在真实条件下修复了 v2 的失败。
- 综合判据 `milestone_four_run_gate_passed = true`。该门槛依赖**独立复算的禁止访问数为 0**（从每个运行的原始访问日志重算），
  而非循环自报的四个安全标记；自报值与独立复算值一致（无隐藏差异）。

## 五、峰值估算方法的标定点（里程碑四第 1 条）

- 全部真实监督运行实测进程峰值内存 ≈ **0.138 吉字节**。
- 参考候选声明峰值 0.35 + 安全余量 0.25 = **0.60 吉字节**，对实测**保守约 4.36 倍**。
- 冻结的估算方法（v3 承载）：候选按“代表性小试验实测峰值 + 固定安全余量”声明包络；启动前与当前容量比较；
  运行中只在候选超己声明包络或系统近-耗尽时停。当前有两个真实标定点（v1 峰值 0.1374、v3 峰值 0.1376，彼此一致）。

## 六、双重独立复核与三处硬化（复核后）

两个互不通气的独立上下文复核了里程碑四：一个从原始字节复验（判定 **CONFIRMED_PASS**，九项自算全对上），
一个功能对抗式审核（判定 **PASS（有保留）**）。功能审核挑出三处真实弱点，均已按测试先行修掉；
三处都不推翻里程碑的事实主张（被审真实路径不受影响），修的是本会话自己写的代码。

- **F1（内存预算默认失效即放行）**：未声明预算时默认为无穷大，候选自占用这条刹车被整条跳过。
  真实运行预算恒有限，被审产物不受影响；但该分支此前无测试。已补特征测试
  `test_undeclared_budget_degrades_to_system_only_supervision`：未声明预算时候选相对刹车故意失效，
  但系统近-耗尽下限仍生效——退化为"仅系统级监督"，绝非"无监督"；并在 `_memory_stop_condition` 注明。
- **F2（"四个安全灯"是自证循环）**：四个安全标记由循环硬编码写死为 False 再被校验器读回，恒为真，
  即便真发生危险行为也照样"灭"，此前被当成已验证门槛呈现——属轻度夸大。已改：校验器改为
  **从每个运行的原始访问日志独立复算禁止访问数**（`decision=="deny"` 计数），运行门槛
  `milestone_four_run_gate_passed` 只依赖这个独立复算值；四个自报标记降级为"仅存档、不计入门槛"，
  并额外核对自报值与独立复算值是否一致。新增单测 `test_supervised_loop_verification.py` 钉死：
  自报标记不进门槛输入；一旦独立复算出真实禁止访问，门槛输入即判负。校验器 schema 升为 `v2`。
- **F3（发布监督身份未锁严格 JSON）**：无穷大预算会静默写出非法的 `Infinity`。已改为无穷大预算序列化成
  JSON `null`（读回时映射回无穷大）并加 `allow_nan=False`；新增
  `test_publish_monitor_target_serializes_an_undeclared_budget_as_strict_json` 钉死。

**强化门槛在真实数据上复验**：对两个冻结的 v3 产物重跑新校验器，结果落于新文件
`supervised_development_loop_v3_r1/VERIFICATION_INDEPENDENT_GATE.json`（schema `supervised_loop_verification_v2`，
**新文件、不覆盖**冻结的 v1 `VERIFICATION.json`）；两次独立复算的禁止访问数均为 0、与自报一致，
`milestone_four_run_gate_passed` 在更严的独立判据下仍为 `true`。

F4–F7（2.87GB 为单点最小值非连续性的推断、停机原因按最新样本归因的文案、1.5× 包络的浮点边界、
任务相对判停的"该停不停"窗口——最后一项的并行聚合门槛已在扩规模清单 §五明确列为未做）
为文案/浮点/已自认设计边界，不影响事实主张，未改。
