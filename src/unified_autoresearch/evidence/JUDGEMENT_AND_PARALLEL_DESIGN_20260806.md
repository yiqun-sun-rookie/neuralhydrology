## 一、极端流域判定规则

### 问题

NSE 的分母是观测方差。方差极小、或方差几乎全来自一两天时，NSE 不再衡量水文技巧，而是衡量
"那一天蒙没蒙对"。64 流域里已经出现 `single_day_variance_share` 高达 0.919 的流域
（09430600 forward：**91.9% 的分母来自一天**）。用中位数一把抓，等于让这些流域和正常流域同权投票。

### 规则（`evaluation/basin_eligibility.py`）

三条判据，**只读验证期真值，绝不读任何候选预测**，且在任何候选运行之前写定：


| 判据 | 阈值 | 理由 |
|---|---|---|
| `zero_variance` | 方差为 0 | NSE 无定义 |
| `zero_flow_fraction` | ≥ 0.5 | 验证期一半以上是干的，NSE 比的那个"平均流量基准"主要在记干旱账，不是水文技巧 |
| `single_day_variance_share` | ≥ 0.5 | 单独一天就占了分母一半以上，分数变成押一天 |

两个阈值都是**无量纲**的，不依赖 mm/day 这类单位，扩到 531 不用重新标定。
任一协议触发即判 unstable（保守）。

三条设计约束：

1. **判定在搜索之前做**，产物用 `O_EXCL` 独占创建，重复写会抛 `FileExistsError`。
   （附带设了 0o444，但**在 Windows 上这只是只读属性、不是保护**——本仓测试助手就有解除它的代码。
   真正拦住覆盖的是 `O_EXCL`。）
2. **unstable 流域绝不丢弃**，单列一组报告。`partition_summary_cells()` 强制两组之和等于全部
   流域，少一个就抛错——headline 数字必须诚实说明自己覆盖了谁。
3. 现有 `scoring.py` 对零方差流域抛异常（会连坐毁掉另外 63 个流域的分）。**该行为未改动**——
   它在冻结产物的路径上。新模块把零方差归类为 unstable 而不是异常，两者并存。

## 二、并行度与聚合资源门槛

### 核心判断：固定并行度这个数本身是错的

清单 §五问"并行度取多少"。实测锚点是占位候选峰值 0.138 GB——**真实候选的体量完全未知**，
按占位候选定的数对真实候选毫无意义。所以不定死一个数，改成**按容量逐批推导**。

### 规则（`protocols/resource_safety_v4.json` + `runtime/resources.py`）

聚合门槛，判"同时启动的这一批的总和"：

```
sum(cpu_cores)   <= 当前可用核数
sum(gpu_count)   <= 当前可用 GPU 数
sum(峰值 + 余量)  <= 当前可用内存 − 内存留白
sum(产出 + 余量)  <= 当前可用磁盘 − 磁盘留白
```

**留白取值直接复用 v3 的停机线**（内存 max(1.5 GB, 4%)、磁盘 max(10 GB, 5%)）。理由：
一批任务绝不能被放行进入"监督器会立刻把它停掉"的状态。这不是新拍的数，是与既有停机策略对齐。

v3 的单任务规则、停机规则在 v4 里**逐字保留**（测试直接比对 v3 文件内容，防止改漂）。

### 并行上限：4，且明确标注为未测量

`max_concurrent_tasks_ceiling = 4`，`default_max_concurrent_tasks = 1`（默认仍是串行，即今天的行为）。

诚实说明这个 4 的地位：**它不是测出来的**。每多一个并发任务就多一个监督子进程，而
"并行下监督自身的开销与日志量"清单里就写着未验证，本次也没测。4 的作用是给这份未知设一个上界，
同时留出有意义的加速；规划器在容量不够时会自动降到 4 以下。协议里写明了：
**要抬高这个数，先测真实并行负载下的监督开销和日志量。**

### 规划器

确定性贪心，按声明顺序装箱，同一输入两次结果逐字相同（测试钉死）。
一个**单独跑都过不了门槛**的任务直接抛错，而不是悄悄推迟——否则会掩盖"这台机器根本跑不了它"。

`max_parallel=1` 时退化为逐个一批，与今天的串行行为一致（测试钉死）。
